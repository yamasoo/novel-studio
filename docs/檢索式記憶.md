# 檢索式長期記憶（`studio/recall.py`）

> 目的：寫第 30 章時，上下文裡要有「作者自己寫過的相似情境」，而不是只有名字對得上的設定檔。

## 為什麼不是「名稱子字串比對」

原本的上下文只會依「這章提到誰」把設定、角色狀態整份拉進來。那解決的是「資料一致」，
不是「寫法連續」——作者寫過的類似場景（同一種張力、同一種對白節奏）完全不會被帶進來。
長篇真正缺的是後者。

## 怎麼做（純本機，不呼叫模型）

1. **切段落**：`正文/` 每一章按空行切段，太短（<40 字）或像標題／表格的段落不當文件。
2. **分詞**：中日文用**字元 bigram**（不用斷詞、不怕新詞），英文用長度 3 以上的單詞。
   查詢用同一套。
3. **BM25 排序**（k1=1.2、b=0.75），取前 k 段。
4. **去噪**：分數低於第一名的 3% 丟掉；與已選段落 Jaccard > 0.8（幾乎重複）只留一段。
5. **依預算裁剪**：注入上限 1200 字（約 600 tokens），超過就少放幾段。
6. **快取**：索引存 `.studio/索引/recall.json`，版本指紋是每個正文檔的「大小＋mtime」；
   任何一章存檔就整份重建。快取寫不進去（書在唯讀位置）也能用，只是每次重算。

## 注入位置

`context.for_chapter()` 在「角色關係」之後、時間線之前，以 **priority 3** 放進
「相似情境（作者自己寫過的段落；參考處境與寫法，不要照抄）」。
查詢＝**本章章綱＋上一章結尾＋這章會出場的角色名字**。
priority 3 代表預算不夠時它可以被丟——它有用，但不是不可取代（續寫合約與章綱才是 priority 0）。

## 實測（25 章合成書，不花錢）

| 項目 | 結果 |
|---|---|
| 索引 | 25 章 → 75 個段落 |
| 第 21 章查「玉珮」場景 | 命中 4 段**全部是玉珮場景**、全部在第 21 章之前（驗收要求 ≥2 段） |
| 會不會撈到未來章節 | 不會（`before=章號` 過濾） |
| 檔案一改 | 指紋改變、索引重建 |
| 上下文成本 | +2.2%（驗收 <15%） |

示範書只有 2 章 7 段，規模太小看不出效果；要比「有沒有幫助」得用 `tools/book_eval.py`
的真 provider 基線（`continue` 任務的 `style_*` 與 `issues`）。

## 怎麼關掉

| 設定（`config.json`） | 作用 |
|---|---|
| `recall: false` | 不注入（索引仍可被其他工具用） |
| `recall_paragraphs: 6` | 注入幾個段落（預設 6） |

## 已知限制

- **完全相同**的段落會被去重成一段（作者貼了兩次、或章節重複的稿子）。
- 段落太短（<40 字）不進索引；對話密集的稿子檢索到的會是描寫段。
- 中文 bigram 對「同義不同詞」不敏感（例如「玉珮」對「佩玉」）。要更準就得接 embedding，
  但那就會呼叫模型、有成本——現階段先用零成本的 BM25。
- 選配的「同角色歷史場景／同地點歷史場景」還沒做；目前是靠把角色名字放進查詢來近似。
