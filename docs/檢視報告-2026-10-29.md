# Novel Studio 專案檢視報告

**檢視對象**：[yamasoo/novel-studio](https://github.com/yamasoo/novel-studio)（v1.16.2，commit `4e20b45`，2026-10-29）
**檢視範圍**：三語（繁中／英／日）維護機制、續寫與「由他書衍生新書」的產品能力、工程風險
**方法**：整份原始碼唯讀掃描＋實際執行專案內建檢查工具＋自行量測（數據見附錄 A）；另寫了一支結構對等檢查器做實測（附錄 B）

## 0. 摘要

**先說結論：這是一個完成度很高的專案，問題不在品質，在「三語的複製貼上式維護」與「續寫缺少可量測的閉環」。**

三個判斷：

1. **三語維護已經是開發主軸，而且靠人力硬撐。** 5 天 36 個 commit 裡有 10 個是三語工作，最近 6 個 commit（v1.15.3～v1.16.2）全部是三語修正。三語資產約 1.35 MB（外掛 3 份 665 KB、語言檔 326 KB、提示詞包 208 KB、README 166 KB），全部手動同步。以目前的量體，**全量重譯一次約 13～20 人日**，每次改版增量約 3～6 小時——這就是為什麼三語修正會吃掉整個開發節奏。
2. **檢查工具做得不錯，但只擋得住「已經存在的鍵」，擋不住「新加的字」與「三份 Markdown 走鐘」。** 實測：`check_i18n.py` 全過，但介面仍有 **13 句使用者看得到的文字沒翻**（英、日各 13）、語言檔躺著 **319／320 個失效舊鍵**、繁中 README 比英日版**少 4 個章節**、範本佔位符三版三種寫法（`{主題}`／`{topic}`／`{項目名}`）。而且**沒有任何 CI**：這些檢查只有「作者記得跑」才會跑。
3. **續寫與衍生新書的底層零件幾乎都在，缺的是連接與驗收。** 逆向拆書、13 項文字指標、整章九步流程、讀者認知帳本、保真檢查都已存在；但寫稿上下文沒有全書／卷大綱、上一章只給最後 1200 字、摘要只給 3 章、文風偏差只有手動按鈕（管線不含）、也沒有任何回歸測試。逆向拆書**不產文風檔**，所以「用某書的文風開新書」目前是兩段手動流程，不是一條龍。

**建議的順序**（詳細見 §5）：

| 批次 | 內容 | 工時 | 換到什麼 |
|---|---|---|---|
| 第 1 週 | CI 閘門、覆蓋率＋清理、術語表、兩個安全修正 | 約 6 人日 | 三語不再靜默破洞；push 就擋 |
| 第 2～3 週 | 結構對等＋新鮮度、翻譯工作流、續寫合約、文風閉環、README | 約 15 人日 | 改一次知道要補哪裡；續寫有量化驗收 |
| 第 4～5 週 | 檢索式記憶、回歸測試 | 約 11 人日 | 長篇注入作者自己的前例；改提示詞可比較 |
| 第 6 週起（選配） | A 書→B 書、漂移偵測、自動駕駛 | 約 19 人日 | 差異化功能；卷末可體檢 |

**不建議現在做**：把三份外掛改成「單一來源＋產生器」（12～18 人日）、把中文原文 key 換成穩定 ID（8～12 人日）。兩者都要先凍結文案格式，而這個專案目前還在高速演進（5 天 36 個 commit），凍結的代價比收益高。先用「事後稽核＋覆蓋率閘門」拿到八成效果，等格式穩了再談產生器。

## 2. 診斷：三語為什麼慢

### 2.1 四個結構性原因

**(1) 中文原文就是 key——改一個字等於換一把鎖。**
`static/i18n.js:45-63` 以中文原文查表，查不到就原樣顯示中文。這個設計讓翻譯可以分批補、不會壞，代價是：**只要中文文案改一個字，英日翻譯就靜默失效，而且沒有任何東西會響**。目前語言檔裡 319／320 個失效鍵就是這樣累積出來的。

**(2) 三份外掛是手抄本，沒有產生器。**
`plugin/`、`plugin-en/`、`plugin-ja/` 各 48～49 檔，找不到任何同步或產生腳本（`tools/` 只有稽核與抽取）。唯一機械化的是「事後檢查」。這代表**每次改一個 skill 段落，要手動改三份、再靠人記得對齊章節**。

**(3) 檢查器驗「一致性」，不驗「覆蓋率」。**
`check_i18n.py:79-109` 只比對 en／ja 兩個語言檔彼此、以及值與 key 的變數；它不拿 `i18n_keys.json`（1,539 鍵）去比對語言檔。所以「原始碼新加一句話、語言檔沒補」永遠不會 FAIL。實測：`check_i18n` 全過，但 13 句介面文字仍是中文。

**(4) 沒有 CI，也沒有測試。**
所有檢查依賴「push 前記得跑」。專案沒有 `.github/`、沒有 `tests/`，`requirements.txt` 只有 5 個下限約束、沒有 lock。以一天 7 個 commit 的節奏，靠自律必然漏。

### 2.3 成本模型：為什麼值得自動化

以中文字數估算（UTF-8 約 3 bytes／字）：

| 資產 | 繁中字數 | 全量重譯工時（800～1,200 字／時） |
|---|---|---|
| 外掛 3 份 | 約 70,900 字 | 59～89 小時 |
| 提示詞包 | 20,757 字 | 17～26 小時 |
| 介面字串 | 22,093 字 | 18～28 小時 |
| README | 約 15,000 字 | 12～19 小時 |
| **合計** | **約 12.9 萬字** | **106～162 小時（13～20 人日）** |

每次改版的增量（依 git churn，語言檔每次約 1,900 行變動）：**3～6 小時**。若一年 50 次改版，光翻譯同步就是 150～300 小時。**把「找缺口、對結構、標新舊」自動化，可省下其中 40～60% 的人力，而且把「漏翻」從常態變成異常。**

### 2.4 順帶發現的工程風險（與三語無關，但會影響可信度）

| 風險 | 位置 | 說明 |
|---|---|---|
| 任意檔讀取 | `app.py:372,386` | `claude_review_job` 直接用用戶端傳來的 `params["path"]` 拼進書目錄讀檔，未經 `project.safe_path`；內容會進審查紀錄。需本機或 CSRF 觸發，但屬實 |
| 無認證／無 Origin 檢查 | 全部變更端點（`app.py:156,1859`） | 只綁 127.0.0.1 是唯一防線；瀏覽器 CSRF／DNS rebinding 可打 |
| 非原子寫檔、備份只到秒 | `tracking.py:175-178,408` | 斷電或 OneDrive 衝突可能得到截斷稿；同秒兩次備份互撞 |
| 任務與事件不回收 | `runner.py:148-188` | 長跑服務記憶體單調成長；主 Claude 任務無逾時 |
| 語言 contextvar 缺口 | `app.py:378,398`；`pipeline.py:139` | 在請求／流程執行緒組提示詞時沒 `set_lang`，en／ja 書可能拿到繁中片段 |

這幾項建議排進第 1 週（見 S1～S5），工時都不高，但都是「出事很難查」的類型。

## 3. 三語改善方案

**設計原則**：繁中仍是唯一來源；譯文是「產物＋基準」；一個指令看狀態、一個指令補缺口、CI 擋回歸。不追求「零人工」，追求「人工只花在判斷，不花在找」。

### T1. CI 閘門（複雜度 S，0.5 人日）

- **做法**：新增 `.github/workflows/checks.yml`（草稿見附錄 C），push／PR 跑 `check_i18n.py`、`check_parity.py`、`prompt_lang_audit.py`。三者都不呼叫真模型，約 1 分鐘。
- **驗收**：故意在 `en.json` 刪一個鍵 → CI 紅；在 `plugin-en` 刪一個檔案 → CI 紅。
- **風險**：低。初期 `check_parity` 會有 40+ 個 WARN，先只擋 FAIL，兩週 burn-down 後開 `--strict`。

### T2. 覆蓋率閘門與一次性清理（S，1.5 人日）

- **做法**：
  1. `tools/check_parity.py` 的 locale 檢查改成拿 `i18n_keys.json` 比對（已實作），缺鍵即 FAIL。
  2. 引入「同形標記」：值寫 `"=="` 表示三語相同（`繁體中文`、`日本語`、路徑類字串），讓覆蓋率能真的到 100%，而不是用假翻譯充數。
  3. 清掉 319／320 個失效鍵（用索引反推，安全：執行期查不到就回中文）；補 13 句真缺的翻譯（附錄 E 已附譯文）。
- **驗收**：`missing = 0`、`stale = 0`、`empty = 0`；`check_i18n` 與 `check_parity` 同時綠。
- **風險**：低。刪鍵不影響執行期；補翻譯要人工看過一次（13 句）。

### T3. 結構對等＋翻譯新鮮度（S，2 人日；原型已完成）

- **做法**：把本次寫的 `tools/check_parity.py`（約 400 行，見附錄 B）收進 `tools/`，補三件事：
  1. 白名單（`tw-terms.md` 這類刻意只存在繁中的檔案），否則永遠誤報；
  2. 擴充檢查「範本佔位符」與「demo `_範本/` 檔案集」——這是目前抓到 A5、A7 的唯一辦法；
  3. `--update-lock` 納入發版流程（`tools/i18n.lock.json` 現為 30 組），把 17 個範本、`demo/`、`CHANGELOG` 也納入。
- **新鮮度機制**（已驗證有效）：lock 記下「繁中檔／en 檔／ja 檔」的 sha256；繁中改了但 en／ja 沒動就 WARN「待更新翻譯」。實測把繁中 skill 加一行 → 立刻出現 `[WARN] fresh 繁中改了、en／ja 沒動：plugin/skills/novel-write/SKILL.md`，還原後消失。
- **驗收**：改一個繁中 skill 段落後，`check_parity` 必須指出「哪三份要更新」；不再需要人工 diff。
- **風險**：低。純新增工具，不動內容。

### T4. 翻譯工作流：缺口 → 初翻 → 人工核可（M，3 人日）

- **做法**：新增 `tools/i18n_fill.py`：
  1. 讀 `i18n_keys.json` 與 locales 的差集（或 lock 指出的待更新檔），依「介面字串／提示詞鍵／Markdown 段落」分組；
  2. 呼叫 `studio/providers.chat`（已有 OpenAI 相容客戶端），提示詞帶**術語表＋前後文＋只給差異片段**，要求輸出 JSON patch；
  3. 寫成 `i18n/pending/<lang>.json` 與 `review.diff`，**不直接改正式檔**；人工核可後 `--apply`。
- **配套**：`tools/i18n_status.py` 一頁看板：各資產缺多少、過期多少、估時多少。
- **驗收**：一次「繁中改 3 個段落」的改版，從「找哪裡要改」到「產出待核可 patch」在 10 分鐘內完成；人工只做核可。
- **風險**：中。AI 初翻會有語氣與術語不一致 → 靠 T5 術語表與「只給差異」壓低；務必保留人工核可關卡，不要自動 merge。

### T5. 術語表（S，1.5 人日）

- **做法**：`i18n/glossary.tsv`（`zh`、`en`、`ja`、`禁用譯法`、`備註`），涵蓋角色、章綱、伏筆、讀者認知、去 AI 味等核心概念；`check_parity` 加一條「譯文含禁用譯法就 WARN」。
- **驗收**：`讀者認知`、`伏筆`、`章綱`、`去 AI 味` 在 UI、提示詞、README 三處用同一個譯法。
- **風險**：低。這是 T4 的前置，也是品質的地基。

### T6. README 減量與對齊（M，3 人日）

- **做法**：兩個選項，選一個：
  - **A（推薦）**：把「安裝、後端設定、常見問題、檔案結構」這些**事實型長段落**搬到 `docs/<lang>/`，README 只留導覽＋三語短版。翻譯面積從 166 KB 降到約 30 KB。
  - **B（最小）**：繁中補齊缺少的 4 節、把「多語系寫作」升為 `##`，讓三份結構一致；接受 166 KB 的維護成本。
- **驗收**：三份 README 標題樹一致（`check_parity` 無 WARN）；所有相對連結都存在。
- **風險**：低。文件搬家不影響程式。

## 4. 續寫與「由他書衍生新書」

### 4.1 現有能力（先說有什麼，免得重做）

| 能力 | 位置 | 現況 |
|---|---|---|
| 逆向拆書 | `studio/reverse.py` | 逐章抽取（1～3 章／批、帶跨批狀態、可斷點續跑）→ 本機合併編號 → AI 整理角色／世界觀／卷綱 → 產出四組草稿（設定／大綱／章綱／追蹤），逐組採用 |
| 文風設計與分析 | `studio/style_design.py`、`studio/shared.py` | 可從描述設計、從樣本分析；13 項文字指標（句長、段長、對白比、標點密度、AI 味信號…）純本機計算 |
| 整章自動流程 | `studio/pipeline.py` | 章綱→寫稿→章綱核對→去 AI 味→審查→修訂→定稿回寫，可從任一步重跑 |
| 長期一致性 | `tracking.py`、`reader_ledger.py`、`fidelity.py` | 狀態卡、角色狀態、伏筆、時間線、讀者認知帳本、去 AI 味保真檢查 |
| 共用庫 | `shared.py` | 文風、章節結構、作者偏好跨書共用，有語言標記 |

### 4.2 續寫的六個缺口

| # | 缺口 | 證據 | 影響 |
|---|---|---|---|
| B1 | 寫稿上下文沒有全書大綱／卷綱 | `context.py:459-495` 只放章綱、狀態卡、上一章尾巴、摘要 | 寫到 30 章後「這章在整本書的位置」只能靠章綱自己，容易走偏 |
| B2 | 上一章只給最後 1,200 字、摘要只給 3 章 | `context.py:475,492` | 聲線與場景連續性弱；伏筆回收靠表格不靠文本 |
| B3 | 檢索是「名稱子字串比對」 | `context.py:174-195` | 找不到「相似情境的前例」，長篇只能靠摘要 |
| B4 | 文風偏差只存在手動按鈕 | `app.py:1739`；pipeline 不含此步 | 生成後沒有自動量測→重試的閉環，「文風像不像」無法驗收 |
| B5 | 沒有回歸測試 | 無 `tests/` | 改提示詞後品質好壞只能憑感覺；不敢重構 |
| B6 | 逆向拆書不產文風檔；匯入的舊書「本書文風」常是空的 | `reverse.py:22` 的 `GROUPS` 只有四組；`shared.create_style` 只能複製既有的 `文風.md` | 續寫別人的書時，聲線只能靠作者自己補，等於最關鍵的一環沒有自動化 |

### 4.3 方案

#### P1. 續寫合約（M，4 人日）

續寫既有書或拆書後，自動生成 `設定/續寫合約.md`：不可變事實（人名、地名、已死角色、已揭示的秘密）、聲線規則（摘自文風檔）、必須承接的懸念（伏筆表未收項）、卷末承諾（卷綱）、禁區（作者偏好）。以 priority 0 注入每章上下文。

- **驗收**：連續 10 章內，契約列出的「不可變事實」零衝突；契約檔可由作者手改。
- **風險**：低。純資料＋注入，不動流程。

#### P2. 檢索式長期記憶（M，6 人日）

新增 `studio/recall.py`：把每章切成段落建索引，用 char bigram BM25（中日免斷詞）＋英文 word token；查詢＝本章章綱＋上一章結尾＋活躍角色；取 top-k 段落，去重、依預算裁剪。可選加「同角色歷史場景」與「同地點歷史場景」兩種檢索。

- **驗收**：20 章以上的書，寫第 N 章時注入的段落有 ≥2 段是「作者自己寫過的相似情境」；上下文成本增加 < 15%。
- **風險**：中。索引要跟著檔案變動失效（用 mtime／hash），否則會檢索到舊稿。

#### P3. 文風保真閉環（M，3 人日）

把現有 `shared.compare`（13 指標）接進寫稿與去 AI 味之後：候選稿偏離文風目標超過門檻 → 自動帶「數字目標＋兩段作者原句」重寫一次；仍偏離則在匯報標記。管線加一步「文風檢查」（可關）。

- **驗收**：demo 三本書各 5 章，平均偏差下降；作者可看到每章 13 指標的「目標／實際」。
- **風險**：低。零件都在，只是接線；注意門檻別太緊（文學本來就會波動）。

#### P4. 書的迴歸測試（M，5 人日）

`tools/book_eval.py`：固定 fixture（三本示範書），三種任務——(a) 遮住第 N 章、用 1..N-1 生成、(b) 去 AI 味固定章、(c) 審查固定章。計分＝確定性指標（文風距離、禁用詞、名字／數字保留率、字數比）＋可選 LLM 評分（固定 rubric）。結果存 `eval/results/<日期>.json`，可與基線比對。

- **驗收**：改一次提示詞 → 一鍵得到「哪些指標退步」；CI 可 nightly 跑（假 provider 驗管線、真 provider 驗品質）。
- **風險**：中。LLM 評分有噪音 → 以確定性指標為主、LLM 為輔，且固定 rubric。

#### P5. 大綱漂移偵測（M-L，6 人日）

每卷結束（或每 10 章）用 reverse 的輕量版重讀自己寫的章節，與卷綱／章綱比對：哪些情節點沒寫到、哪些新增事件沒進大綱、哪些角色消失。產出「偏離報告」＋可選重規劃。

- **驗收**：卷末報告能列出 ≥3 條具體偏離，並可一鍵產生「更新卷綱」草稿。
- **風險**：中高。重讀成本（token）要控制；只讀摘要＋章末，不讀全文。

#### P6. 由 A 書產生 B 書（L，9 人日）

這是使用者第二個需求的完整解。六步：

1. **風格指紋**：對來源書跑 `style_metrics`（13 指標）＋LLM 抽取「13 個文風面向」＋10 段代表性短句（≤120 字）。存 `設定/風格指紋.json`。
2. **結構 DNA**：只取抽象特徵——視角、時態、章長分佈、場景／續景比例、對白比例、弧線形狀、套路清單。**不取**人名、地名、專有名詞、事件序列。
3. **新故事生成**：premise → 角色 → 世界觀 → 卷綱 → 首卷章綱（重用既有 `novel-outline`／`novel-setup` 的提示詞與 skill），硬約束「不得沿用來源作品的角色名、地名、專有名詞、事件順序」。
4. **相似度護欄**：生成稿與來源書的 char 6-gram Jaccard、名稱重疊、最長共同片段；超過門檻就標記並要求重寫該段。
5. **建專案**：骨架＋`設定/文風.md`（含文字指標）＋`設定/章節結構/`＋前三章章綱。
6. **接現有流程**：直接進「整章自動流程」。

- **驗收**：從一本來源書到「可開寫的新書資料夾」≤ 10 分鐘操作；相似度報告無超標段落；新書文風指標落在來源書 ±15% 帶內。
- **風險**：中高。法務與原創性是主要風險 → 護欄必須是硬性的（超標就不能存檔），並在資料夾記錄來源與授權狀態。
- **注意**：這條流程**只能用於公有領域或作者自有作品**；對他人著作僅取「抽象特徵」仍有爭議，建議在 UI 明確提示，且預設關閉「上傳他人作品」選項。

#### P7. 批次續寫的自動駕駛（M，4 人日）

現有流程已能「連續寫到最後一章」。加上檢查點：每 K 章暫停、跑 P3 文風檢查＋P5 漂移偵測＋花費統計，通過才續跑；偏離超標就停在該章等人。等於把「品質」變成流程的一部分，而不是事後補救。

- **驗收**：一次跑 10 章，中途至少一個檢查點；偏離時確實停下並給出原因。
- **風險**：中。停下條件太多會煩人 → 預設只擋「P0 一致性」與「文風偏差 > 2 倍門檻」。

## 6. 驗收標準（Definition of Done）

**三語**

1. `check_i18n`、`check_parity`、`prompt_lang_audit` 在 CI 綠，且 `check_parity --strict` 無 WARN。
2. locale 覆蓋率 100%（含 `"=="` 同形標記）、失效鍵 0、空值 0。
3. 三份 README 標題樹一致；`demo/*/_範本/` 檔案集一致。
4. 任一繁中 skill 段落改動，`check_parity` 能指出「en／ja 待更新」。
5. 新增語言（例如韓文）的工程量從「一週」降到「兩天」——這是 T3＋T4＋T5 的綜合驗收。

**續寫／新書**

6. 連續 10 章：續寫合約的不可變事實零衝突；文風指標偏差在示範書校準的帶內。
7. 每章上下文成本增加 < 15%，生成品質（回歸分數）不退步。
8. A 書→B 書：10 分鐘內產出可開寫的專案；相似度報告無超標；文風指標落在 ±15% 帶內。
9. 任一提示詞改動，`book_eval` 產出前後對比，能指出退步的指標。
