# 開書流程改版規格（前段：開新書 → 訪談 → 下一步）

狀態：規格稿，尚未動程式。實測樣本：《太空牛仔》（E:\dev\novel1\太空牛仔，82 筆任務紀錄）。
範圍：書架「開新書」→ 建立後總覽 → 開書訪談 → 訪談結束後的下一步引導。
不含：章節寫作、整章自動流程、設定集、插圖（那些目前是順的）。

## 0. 一句話

把「開新書」從 6 個決定的表單縮成 2 欄 + 一鍵；建立後總覽立刻說「訪談在右側跑」；訪談在面板用可點的選項卡問完；結束時給一頁報告，之後永遠只有一顆「下一步」。

## 2. 問題清單（依影響排序）

### P1 建立後的落點錯：明明是「進行中」，畫面說「還沒開始」
- 建立後 page_shelf.js:113-123 直接 `FE.go("#/b/" + id)`；setup_new 任務已在跑。
- 總覽頁因為還沒有 CLAUDE.md 走 renderNonBook（page_overview.js:56-92），標題寫「這個資料夾還不是小說專案」，主要按鈕是「開始開書訪談」（page_overview.js:88）。
- 後果：作者以為要再按一次；按下去會再開一個 setup_new（每個都是新任務、各自獨立）；把面板關掉就完全找不到訪談。
- 註：page_shelf.js:116 的註解已經承認骨架模式有這個問題並繞開，訪談模式沒有繞。

### P2 訪談沒有可點的選項，只能手打代號
- 面板本身有完整的提問 UI：選項按鈕 + 自由輸入 + Ctrl+Enter（vendor/fekit/fe/jobs.js:715-757）。
- 但工作室只在「任務已結束」時塞一個假提問 `{"id": "reply", "prompt": "要接著做什麼？"}`（ns_jobs.py:157-160），執行中的任務永遠不會有 ask。
- 而且回覆端一律開新任務，不會回答正在等的提問（ns_jobs.py:345-358；app.py:2501-2502 執行中直接 409）。
- 對照訪談流程本身假設「有提問工具（多選題介面）就用它」（plugin/skills/novel-setup/references/interview.md:5）。
- 實測結果：作者打出「A. B. A.中篇 10～30 萬」「a a a b a」這種字串 28 次。

### P3 沒有「訪談結束」這個狀態，下一步順序被跳過
- 三份檔案 19:50 就寫好，App 沒有任何「開書完成」的表示；總覽頁第一顆主要按鈕是「排第1–10章的章綱」/「寫第N章」（page_overview.js:129-136）。
- 正確順序是 故事核心 → 全書大綱 → 第一卷卷綱 → 前 10 章章綱 → 第 1 章；這條線只存在於大綱頁四顆平權按鈕（page_outline.js:151-155），沒有主次。
- 後果：作者在回覆框裡自己找路（20:08 用回覆寫全書大綱），花掉 50 分鐘。

### P4 回覆框沒有定位，變成萬用聊天
- 標題一律「回覆」（app.py:2236-2237），提示一律「要接著做什麼？」（ns_jobs.py:160）。
- 每次送出都是新任務、對話不連續；正式動作（故事核心診斷、全書大綱、卷綱）都被繞過。
- 作者選擇保留它為主要互動、只加提示文字（本次決定）。

### P5 開新書對話框一次要 6 個決定，還有兩個重疊的軸
- page_shelf.js:46-96：書名、語言、初步構想、參考書、開書方式（訪談／骨架）、順便產生骨架草稿。
- 「開書方式」與「順便產生骨架草稿」重疊：都跟參考書有關，但一個要求必選參考書（:105）、一個沒選就跳錯誤 toast（:126）。
- 說明小字四段（:61、:64、:67、:91），第一次用的人看不懂「開書訪談」是什麼，只能先按了再說。

## 3. 目標流程

```
(書架) --開新書(書名+一句話+語言)--> (總覽: 開書進度 1/5, 訪談進行中)
   --> 面板: 第一輪 4 題(按鈕) --> 第二輪 4 題(按鈕) --> 第三輪(選問, 可跳過)
   --> 一次寫出 CLAUDE.md / 故事核心 / 文風 + 開書報告(已填/待補/下一步)
   --> 總覽: 進度 2/5「下一步：故事核心診斷」--> 3/5 全書大綱 --> 4/5 第一卷卷綱
   --> 5/5 前 10 章章綱 --> 寫第 1 章(原本就順的段落)
```

規則：任何時刻總覽只有一顆 primary 按鈕，就是下一步；其他動作全部次要。

## 6. 驗收條件
1. 開新書對話框預設只看到 3 個欄位；不展開進階也能用訪談模式開書。
2. 開書後 2 秒內總覽出現「開書訪談正在進行／打開右側面板」，且頁面上沒有第二顆「開始開書訪談」的 primary。
3. 訪談全程可以只靠點按鈕走完兩輪（不輸入任何文字）；第三輪有「跳過」。
4. 任一題按「跳過，你決定」→ 檔案有內容、報告標「（預設）」。
5. 訪談完成 → 面板出現報告卡，列出實際寫入的檔案（程式檢查，不是模型自述）；缺的標「待補」。
6. 報告卡的「下一步」與總覽頁的 primary 指向同一個動作（故事核心診斷）。
7. 依序完成五步後，primary 才變成「寫第 1 章」。
8. 回覆框在非訪談任務的提示文字為「補充需求…」，且上方說明寫著「正式步驟請用上面的下一步／動作按鈕」。
9. 既有書（已有 CLAUDE.md）打開總覽的行為不變。

## 7. 風險與已知問題
- **ask 阻塞**：`job.ask(wait=True)` 會讓 worker thread 停住等作者。目前 runner 是每本書一個任務，還算安全；但要在 UI 明講「等待你回覆」的 chip（jobs.js:776 已有）。
- **Claude Code 模式沒有 ask**：claude -p 非互動（studio/runner.py:313-326 stdin 關閉），訪談在該模式只能退回文字回覆。規格：Claude Code 模式顯示「這個模式沒有選項按鈕，建議切到 API 執行者」並允許照舊文字回覆。
- **五步判定依賴檔案內容**：作者手動編輯檔案可能誤判；判定要寬鬆（字數門檻）並提供「手動標記完成」。
- **附帶觀察（已查清，2026-11-08）**：《太空牛仔》的 `設定/章節結構` 不是任務副作用、也不是舊版殘留，而且**不是空資料夾**。
  裡面有 `設定/章節結構/起承轉合.md`（913 bytes），資料夾建立時間 19:57:30.177。
  來源是「共用庫 → 章節結構 → 套用到書」：`studio/shared.py:537` 的 `BOOK_STRUCT_DIR`、`apply_structure()`（:552-562）建立目錄並寫檔，`set_book_default()`（:565-574）在 frontmatter 加 `預設: 是` 並備份。
  鐵證是 `.studio/備份/改預設結構前_起承轉合.1794052650.md`，檔名時間戳正是資料夾建立的秒數，內容與 `studio/presets/結構/起承轉合.md` 只差那行 `預設: 是`。
  19:47–20:00 之間沒有任何任務的事件跨越 19:57:30，所以是 UI 操作（`app.py:801-807` 的 `POST /api/shared/structures/{name}/apply`），不是模型跑的。
