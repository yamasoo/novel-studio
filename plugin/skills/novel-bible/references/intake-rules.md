# 設定入庫規則

## 一、三種來源，同一條入口

| 來源 | 例子 | 進哪裡 |
|---|---|---|
| 作者自己寫的 | 作者貼一段角色介紹、直接改檔案 | 作者明說「就這樣」→ 正式；否則先問一句「直接定案嗎？」 |
| 從對話萃取 | 聊了半小時世界觀，說「把剛剛確定的整理起來」 | 作者**明確同意過**的 → 正式；只是討論過、沒拍板的 → 草稿 |
| AI 生成 | 「幫我生成 5 個配角」「設計這國家的稅制」 | 一律先進 `設定/草稿/`，作者確認後才轉正式 |

判斷不了是否「已確認」時，放草稿。草稿放錯的代價很小，正式設定放錯會污染正文。

## 二、從對話萃取的做法

1. 回頭看這次對話（或作者貼上的對話紀錄），列出所有被提到的設定元素。
2. 每一條標記狀態：
   - **已定案**：作者說過「好」「就這樣」「我喜歡這個」，或作者自己提出且沒被推翻。
   - **討論中**：提過幾個選項、還沒選；或作者說「再想想」。
   - **已否決**：作者說不要的。
3. 被推翻過的，以**最後一次**的說法為準。
4. 已定案的寫入正式檔；討論中的寫進草稿並註明候選選項；已否決的不寫（除非作者要你記「不要做什麼」，那寫進名詞表的注意欄或角色的備註）。
5. 匯報時用表格列出：哪些進了正式、哪些進了草稿、哪些沒收。

## 三、草稿轉正式

作者說「草稿裡的 X 可以了」「這幾個都定案」時：

1. 讀草稿檔，套用正確範本（`_範本/角色.md` 等）整理格式。
2. frontmatter `狀態` 改成 `正式`，移到對應正式資料夾。
3. 檢查和既有正式設定有沒有衝突（同名、矛盾的規則、關係對不上）。有衝突先問作者。
4. 名詞表補登記新名詞。
5. 刪除草稿檔。

## 四、寫完章節後的登記（接 novel-write 的申報）

novel-write 寫完一章會列出「寫了要報」的新增物。你負責把它們登記進資料庫：

| 新增物類型 | 登記到 |
|---|---|
| 具名配角 | `設定/角色/{名}.md`（定位：配角；只填正文已出現的資訊，其他欄位留空） |
| 新勢力 | `設定/勢力/{名}.md` |
| 新規則、能力表現、地理或制度細節 | 對應的 `設定/世界觀/{主題}.md`，加一條規則 |
| 新名詞、新稱謂 | `設定/名詞表.md` |
| 新伏筆、新關係、新承諾 | 這些是「事實」，由 novel-write 寫進 `追蹤/`，不在這裡處理 |

登記時**只寫正文已經寫出來的資訊**，不替配角補背景故事。要補，先問作者或放草稿。

## 五、衝突處理

發現兩處設定互相矛盾時：

1. 不要自己選一邊改掉。
2. 列出：矛盾的兩處（檔案、原文）、各自被哪些已寫章節引用。
3. 給作者 2～3 個處理選項，標出推薦。通常推薦「以正文已寫出的為準」，因為讀者已經看到了。
4. 作者決定後，改設定檔；若需要改正文，交給 novel-write 的改稿流程。

## 六、命名規則

- 檔名就是該設定最常用的名稱，例：`林晚.md`、`天機閣.md`、`力量體系.md`。
- 別名寫在 frontmatter 的 `別名`，不要為別名另開檔。
- 同名不同人：加區分詞，例：`王伯（林家管家）.md`。
- 名稱一律繁體，避免異體字混用（例：「台」與「臺」選一個並登記在名詞表）。
